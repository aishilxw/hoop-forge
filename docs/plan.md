## 1. 产品定位、用户与交付范围

### 1.1 给玩家的一句话

从现役球员卡中继承九项能力，打造你的原创球星，调整打法，经历三个赛季并争夺冠军。

主要用户：熟悉 NBA 球员特点、喜欢阵容搭配/能力比较/生涯模拟的篮球游戏玩家。首轮试用优先找 3–5 位符合这些行为的人，而非仅仅“知道 NBA”的人。

首局体验目标：一分钟内理解选卡规则，五分钟左右完成创建并看到第一场比赛结果。时间为设计目标，需实测，不作为已经验证的结论。

### 1.2 必须做完的 P0

1. 完整现役球员快照与九维评分，数据来源和估算标识可查。
2. 开局 20 抽，5 明星＋15 非明星，无重复人物。
3. 九维分配、来源预览、不可重复使用同一卡、确认创建。
4. 四种打法，固定队友，若干明确风格的对手。
5. 短赛季、季后赛、个人数据、赛后分析、金币结算。
6. 普通抽卡与位置定向抽卡；能力继承与训练。
7. 本地保存、恢复、导出、导入、重新开档保护。
8. 统一中文界面，电脑优先，手机能够完成核心操作。
9. GitHub 可复现源码；可下载离线运行包；中文 README、验证记录。
10. 笔试配套：1000–2000 字图文教程、300 字以内创作说明，截图来自真实运行。

### 1.3 P1：P0 全部完成后再考虑

- 根据真实数据生成的 AI 球探/赛季报道；首发可由确定性模板实现，并明确称为赛后分析。
- 漂亮的分享海报、更多对手风格、抽卡稀有演出。
- 1–3 分钟剪辑字幕视频。时间紧时优先完成题目允许的图文方案。

### 1.4 首发不纳入

实时篮球操作、3D、全联盟球队管理、球员交易、联网对战、排行榜、账号、付费抽卡、实时名单同步、伤病/薪资/合同、完整 NBA 官方规则复刻、桌面安装器。

限制的是首发工程范围，不改变“全部现役球员可供抽取”的用户要求。球员池和对手球队是两个概念：真实球员提供能力；对手是本游戏设计的虚构球队。

## 2. 统一游戏规则：所有 Agent 必须按同一版本实现

本节所有初始数值进入 `src/config/balance.ts`。不得在 Vue 文件、测试夹具和模拟器中各写一份。

### 2.1 九维、标识与定义

| 中文 | 固定字段名 | 主要影响 |
|---|---|---|
| 内线得分 | insideScoring | 近筐出手的命中率 |
| 外线得分 | outsideScoring | 外线三分出手的命中率；首发不另设中投属性 |
| 内线防守 | interiorDefense | 限制对方近筐效率、盖帽机会 |
| 外线防守 | perimeterDefense | 限制外线效率、制造部分持球失误 |
| 组织 | playmaking | 创造队友机会、助攻归属与传球稳定性 |
| 运球 | ballHandling | 持球失误率、个人创造机会 |
| 速度 | speed | 转换机会、摆脱与回防 |
| 身体 | physicality | 力量与对抗，影响内线终结和卡位 |
| 篮板 | rebounding | 投篮不中后的进攻/防守篮板归属 |

- 全部是 40–99 的本游戏能力整数，不冒充 NBA 或商业篮球游戏的官方评分。
- 综合能力仅为界面参考：九维算术平均、四舍五入。模拟器不得仅用综合能力决定胜负。
- 身高/位置/球衣号仅为展示信息；首发不暗中给身高加成。
- 命名和排序必须全工程一致；界面中文映射由共享常量导出。

### 2.2 明星池与初始抽卡

1. 数据 Agent 提交 `star-pool.json`：建议 40 人，逐个核对现役身份、选择理由与数据日期。最终以负责人通过的名单为准，不按临时模型回答决定。
2. 明星池与非明星池互斥，初始分别均匀无放回抽 5 和 15 人。
3. 创建流程先保存种子和抽卡结果，再播放动画。刷新不能重抽同一个开局。
4. 开局角色未确认前可自由分配和撤销，不消耗卡；确认必须恰好填满九项、使用九个不同实例。
5. 每个实例对应一个 NBA 球员。初始九张卡消耗，记录各维度来源；未使用 11 张成为库存。
6. 初始金币为 0。确认界面应明确提示“使用 9 张、保留 11 张”，不可只在说明文档写。
7. 对球员池不足、明星数不足、重复 ID 报明确数据错误，不通过放回抽样凑数。

### 2.3 打法

固定枚举：`primaryCreator` 持球核心、`offBallScorer` 无球得分手、`interiorAnchor` 内线支柱、`teamOrganizer` 团队组织者。

| 打法 | 原创球员初始进攻使用权重 | 原创球员三分倾向 | 助攻贡献系数 |
|---|---:|---:|---:|
| 持球核心 | 0.34 | 0.40 | 1.00 |
| 无球得分手 | 0.26 | 0.70 | 0.70 |
| 内线支柱 | 0.27 | 0.08 | 0.60 |
| 团队组织者 | 0.19 | 0.35 | 1.35 |

- 上述是初始调参值，不宣称符合真实 NBA 概率。
- 其他四名队友平分剩余使用权重，再乘各自固定进攻偏好并归一化。
- 打法不直接增加属性；通过事件概率、出手分配、传球等影响结果。
- 比赛前可换打法，比赛进行中锁定。所有比较测试须锁定队友、对手及随机种子。

### 2.4 赛季与生涯

- 一次生涯最多三个赛季；每季 12 场常规赛。每场都有唯一 `matchId`。
- 常规赛至少 6 胜进入季后赛；未达标进入赛季结算。
- 季后赛半决赛、决赛均为三局两胜；每轮先赢两场即停止，不多模拟不存在的第三场。
- 对手使用 4 类虚构模板：外线投射、内线强攻、强硬防守、快速转换。每季常规赛各遇 3 次，顺序由种子打乱。
- 固定四名队友；不开放组队管理，避免 scope 扩张。
- 第二、三季对手模板分别小幅增强，初始建议各项 +1/+2，上限 99；调参后写入版本。
- 增强相对原始模板为第1/2/3季 +0/+1/+2，不在上一季结果上累计。季后赛在此基础上半决赛额外 +1、决赛额外 +2。
- 创建赛季时，从四类模板中无放回选两个作为半决赛/决赛对手，保存模板ID、完整属性快照与每场种子；同一系列赛使用同一对手。赛季未晋级时保留计划但不产生已比赛记录。
- 第一、二季结算可进入休赛期，第三季结算后生涯结束。夺冠后仍可完成后续赛季，争取更多冠军。
- 展示“本游戏短赛季”，不声称这是真实 NBA 赛程、排名或预测。
- 不生成无依据的“联盟排名”；先显示自己的胜负、晋级门槛、系列赛比分。

### 2.5 可操作窗口

| 状态 | 允许操作 |
|---|---|
| 开局选卡 | 分配、撤销、确认创建；不能抽付费包和训练 |
| 常规赛/季后赛赛前 | 查看卡、抽包、继承、训练、调整打法、开赛 |
| 比赛模拟中 | 查看进展、跳过动画；所有数值与经济操作锁定 |
| 赛后结果 | 查看已结算奖励、继续；点击继续不会再发钱 |
| 赛季结算 | 查看阶段奖励、进入休赛期或结束生涯 |
| 休赛期 | 抽卡/改造/调整打法、开始下一季 |
| 生涯结束 | 查看、导出、分享、确认后新开档；不再消费旧档金币 |

### 2.6 抽包、继承与训练

- 普通包：90 金币，1 张卡；先以 10% 概率选明星池，否则选非明星池，再池内均匀抽取。
- 位置定向包：120 金币，1 张卡；先选后卫/锋线/内线分类，再按同样 10% 规则在该分类抽取。数据验收要求每个分类的两个池均非空。
- 位置分类由数据文件明确给出：每人恰好一个抽卡分类，双位置不能导致重复进入候选池。
- 后续抽包允许抽到已有球员；每次生成新的 `cardInstanceId`，两个同名实例不能互相覆盖。
- 概率在抽卡页可见。不加隐藏保底，不让客户端临时调整概率。
- 继承：消耗 1 张卡，选其中 1 项；只有来源数值高于当前值才允许确认。其他八项不变，不另收金币。
- 训练：选择属性和若干卡，每次成功 +1；40–79 需 3 张，80–89 需 4 张，90–98 需 6 张；另收 30 金币。99 不可训练，不扣费。
- 训练卡不限稀有度，但必须由玩家明确选择；不得自动消耗最好的卡。
- 全部消耗一次提交，库存不够/金币不够/状态不允许时整个动作失败，状态不变。
- 来源记录包括最初贡献者、后续继承者、训练增加量，用于详情页与赛季卡。
- `lineage.trainedPoints` 只记录最近一次继承后的训练增加量。再次继承时直接替换当前值并清零此字段，不能在新值上再加旧训练点；历史训练另存简短成长事件。

### 2.7 金币、奖励与重复结算

- 每场基础奖励 20；获胜额外 15；角色表现奖励 0–10。
- 常规赛晋级奖励 60；赢半决赛奖励 80；冠军奖励 160；都是一次性里程碑。
- 角色表现按当前打法计算：得分手看效率与得分、组织者看助攻与失误、内线支柱看篮板/盖帽及终结。每项映射与上限必须写在配置中。
- 原型映射建议：得分奖励 `min(10, floor(points / 4))`，再按投篮效率给 0.6–1.0 系数；组织奖励 `clamp(floor(assists * 1.5 - turnovers), 0, 10)`；内线奖励 `clamp(floor(rebounds * 0.6 + blocks * 1.5), 0, 10)`。持球核心取得分和组织奖励平均。计算只用实际事件汇总数据。
- 效率统一用 `eFG = (FGM + 0.5 * threePM) / FGA`。系数：低于0.40为0.6，0.40至低于0.55为0.8，至少0.55为1.0。先按打法计算原始奖励，再统一 `floor(clamp(rawReward, 0, 10))`，金币始终为整数。阈值与系数在balance中只定义一次。
- 零出手的效率不除零，得分型表现奖励为 0。
- 不把失分都归责到个人；没有防守归因数据就不发明“你让对手少得 15 分”。
- 比赛结果、奖励记录、金币余额、赛程推进写入同一个状态快照，再播放结算动画。
- 重复请求、双击、刷新后再次进入结果页，只能返回已有结果，不能新增奖励。
- 本地游戏不承诺防篡改、防读档；保证正常使用一致性即可，不做无意义的线上反作弊工程。

## 3. 比赛模拟器实施规范

### 3.1 模拟层级与边界

采用简化回合事件模拟，结果由程序计算。界面只展示，不参与判定。首发不包含犯规罚球、伤病、挑战、暂停战术等完整规则；比分只来自两分和三分投篮，README 与帮助中明确说明。

每场先用固定种子抽取 90–104 个基础进攻回合/队，双方交替进行。常规时间48分钟，最小六人名单：原创球员、四名固定队友、一名固定替补。首发采用明确的简化轮转：原创球员在第0–8、12–20、24–32、36–44分钟出场，共32分钟；替补补其余16分钟；四名队友全场。对方也采用同样六人结构，不加入疲劳模型。

第j个初始球权的逻辑时刻为 `48 * j / (2 * possessionsPerTeam)` 分钟，j从0开始；该球权中的篮板与追加出手沿用同一在场阵容。加时双方各10个初始球权/队、时长5分钟，原创球员与四名队友全程在场。每次事件恰好5人在场；全队分钟合计必须为比赛时长的5倍。未在场球员不得获得出手、助攻、篮板等事件。

### 3.2 每次进攻的固定事件顺序

1. 从场上五人和打法权重选择进攻发起者。
2. 根据运球、组织、对方外防判断失误；成功抢断只占失误的一部分，其余记普通失误。
3. 未失误时，先决定是否传球；传球则另选接球者，否则发起者自己出手。
4. 按最终投篮人的打法/模板决定近筐或外线出手，再计算命中概率；所有概率有上下限。
5. 近筐出手允许部分未命中归为盖帽，盖帽必须同时计入对方的一次投篮未中。
6. 命中后记录得分、命中数、助攻（如有），交换球权。
7. 未命中时分配进攻/防守篮板；进攻篮板可继续进攻，但单次初始进攻最多 3 次二次进攻，防止极端循环。
8. 写事件记录，聚合统计；不另行随机生成漂亮的赛后数据。

传球时另选一名不同的场上球员作为接球者，实际投篮使用接球者属性；仅该次接球投篮命中才可给传球人助攻，不能自助攻。发生进攻篮板后清除上一投篮的助攻候选。达到三次二次进攻上限后再次未中，简化为防守方得到篮板并结束球权，不能先记进攻篮板再无事件地换球权。

### 3.3 初始概率公式（必须集中配置并经实测校准）

- `turnoverP = clamp(0.13 + (oppPerimeter - handlerHandle) * 0.0015 - (handlerPlaymaking - 70) * 0.0005, 0.04, 0.24)`。
- `insideP = clamp(0.50 + (insideScoring - oppInterior) * 0.003 + (physicality - oppPhysicality) * 0.001 + creationBonus, 0.28, 0.76)`。
- `outsideP = clamp(0.34 + (outsideScoring - oppPerimeter) * 0.0025 + creationBonus, 0.18, 0.55)`。
- 传球概率初始为 `clamp((0.30 + (handlerPlaymaking - 70) * 0.004) * styleAssistFactor, 0.15, 0.70)`；传球时在其他四人中按进攻权重选择接球者。
- `creationBonus` 为传球加成与速度加成之和，再限制到0–0.06：传球加成为 `clamp((passerPlaymaking - 60) * 0.001, 0, 0.04)`，没有传球则为0；速度加成为 `clamp((shooterSpeed - matchupSpeed) * 0.001, 0, 0.02)`。每项单独记录，便于分析来源。
- 投篮对位防守值采用60%直接对位者＋40%对方场上均值；篮板公式中的双方能力采用场上五人均值。双方先按固定槽位配对，替补继承原创球员槽位，不由各Agent临时猜对位。
- 进攻篮板率建议 `clamp(0.24 + (offRebound - defRebound) * 0.002 + (offPhysical - defPhysical) * 0.0005, 0.10, 0.40)`；归属按场上球员篮板权重抽样。
- 防守属性必须使用当前场上人员计算，不能用一个无来源的敌人总分代替。
- 这些是可测试的游戏模型，不是现实球员统计预测模型。不能把游戏模拟胜率用于宣称真实比赛结论。

### 3.4 平局、加时、随机性与动画

- 常规结束平分则进行 5 分钟加时，双方同样数量基础进攻回合，再检查比分；必须真实生成加时事件，不能直接给一方加 1 分。
- 加时用同一比赛随机流继续。设置异常执行预算；超过预算返回可诊断的模拟失败，不能把技术失败记成球员输球。
- 每场输入包括双方阵容、打法、属性快照、`matchSeed`、规则版本。相同输入必须给出相同结果。
- 抽卡随机流与比赛随机流分离；预览、排序、打开弹窗不能消耗随机数。
- 比赛种子来自 `careerSeed + seasonIndex + matchId` 的稳定哈希。算法和整数处理写进测试向量，禁止 `Math.random()` 进入 domain。
- 一场可先在内存完成计算，再提交结果并渐进播放事件；跳过只影响动画，不影响结果。重启后直接恢复已保存结果。
- 大量赛季验证走无界面批处理；正常单场目标低于 300ms（记录实际机器），超标先分析，必要时迁入 Worker，不预先增加复杂度。

## 4. 球员数据工程：完整性是正式交付门槛

### 4.1 快照定义与文件

计划数据日期为实施当天，不能因为本文日期而假称已核验 2026-10-29 名单。验收时必须给出实际 `asOfDate`。

| 文件 | 内容 |
|---|---|
| `data/source-manifest.json` | 每支球队的名单来源、采集时间、纳入规则、统计来源和许可/再分发记录 |
| `data/raw/` | 可再分发的原始快照；不能再分发的源不放仓库，保留合法来源说明 |
| `data/overrides.json` | 人工修正的球员、字段、原因、证据、修改人 |
| `src/data/players.json` | 运行时精简名单、九维、位置分类、来源与置信标识 |
| `src/data/star-pool.json` | 明星 ID 列表和选择依据 |
| `src/data/roster-meta.json` | 数据日期、实际人数、队伍覆盖、数据版本、来源说明 |
| `scripts/validate-data.ts` | 完整性、范围、重复、明星池与位置池检查 |

### 4.2 采集与验收

1. 先读取 NBA 官方队伍/名单页面和可访问公开资料，确认当期 30 队名单；使用稳定 ID，不能靠中文译名连接数据。
2. 建立“球队 → 纳入球员 ID”清单，对交易与双向合同进行交叉检查。跨队重复人物去重，并保留明确的快照归属。
3. “全量”以冻结的来源清单逐人对账，不能用一个猜测总人数或“已收集 400 多人”代替。
4. 先用小样本夹具让界面和 domain 并行开发；夹具必须标记 `fixture`，正式构建禁止引用。
5. 数据访问受限时记录具体缺口，换可核查公开来源或请用户提供数据；不伪造球员、评分证据，不绕过访问控制。
6. 完整名单未过关时，可以演示原型，但不能标记为满足“所有现役球员”的正式版。

### 4.3 九维评分方法

- 参考最近完整赛季为主体，当前赛季仅在有足够样本时小权重补充；具体时间窗在数据任务中冻结。当前少量比赛不能直接决定全部能力。
- 出手类同时考虑效率与样本量，不把一次出手命中率 100% 的球员评为顶级。
- 低样本估计向位置先验收缩，保存置信等级；新秀/伤缺使用可解释的估算与显式标注。
- 先将可用指标标准化，再映射到 40–99。各维的指标、权重、缺失值策略写成 `docs/data-methodology.md`，负责人审核后批量计算。
- 外线得分参考三分频率、命中率和出手量；内线得分参考近筐数据；组织参考助攻与失误相关指标；篮板参考篮板率与机会数据。
- 防守、速度、运球、身体不能用单一统计机械推断。缺失时采用公开证据＋明确人工估计，标为 estimated，不让模型凭印象批量填满后隐藏来源。
- 九维评分不追求三天内建立专业球探模型，追求可解释、一致、完整、可修改。
- 保留逐项评分依据类型；评分和明星身份分开，不让角色球员因为不是明星而失去单项高分。
- 原版头像、球队 Logo 和商业游戏评分不作为必需素材；首发采用名字、号码和原创几何球衣图，减少素材依赖。

`CareerState` 必含：存档/规则/数据版本，careerId、revision、careerSeed、抽卡随机状态、阶段、初始 20 卡、原创球员、库存、金币、赛程、比赛结果、里程碑记录、已应用 commandId。比赛结果携带参与球员属性与打法快照，不能因之后融合改变历史成绩。

领域错误只返回code和参数，中文提示由application/UI统一映射；存储失败、导入体积超限等属于应用错误，单独建类型，不混入纯domain。

### 5.4 对外函数与命令

| 接口 | 要求 |
|---|---|
| `createCareer(seed, catalog, versions)` | 纯计算初始卡并返回合法初始状态；应用层保存成功后才展示 |
| `previewDraftAssignment(state, assignments)` | 纯预览，不消耗、不推进 RNG |
| `applyCommand(state, command, catalog)` | 返回新状态＋领域事件或明确错误；失败不修改原状态 |
| `simulateMatch(input)` | 纯计算，返回事件、双方数据、比分、种子与版本 |
| `calculateMatchReward(result, style)` | 纯计算，无任何余额写入 |
| `validateSave(raw, catalog)` | 不可信输入校验，返回完整可加载状态或错误 |
| `buildSeasonSummary(state)` | 只读已有比赛，不随机捏造数据 |

命令最少包括：`CONFIRM_DRAFT`、`BUY_PACK`、`INHERIT_ATTRIBUTE`、`TRAIN_ATTRIBUTE`、`SET_PLAY_STYLE`、`PLAY_NEXT_MATCH`、`ACK_MATCH_RESULT`、`START_NEXT_SEASON`。统一包裹 `commandId` 与 `expectedRevision`。

UI 不直接操作金币和库存，不在组件里调用模拟器写状态。统一通过 `gameService.execute(command)`，由它完成校验、domain 运算、一次保存和 store 更新。

命令处理顺序固定：取得写锁并读取最新合法状态 → 查询commandId是否已应用 → 已应用则返回已有状态与记录，不再检查旧revision并重做 → 新命令才检查expectedRevision → 纯domain运算 → 持久化 → 更新store。同一用户操作及其重试复用commandId；保存失败不记录已应用。两个有意发起的新抽包属于两个命令，不能因为参数相同而永久去重。抽卡结果未关闭前暂不允许发起下次购买，避免双击产生两个不同命令。

### 5.5 持久化与恢复

- 首发一个活动档，另保留上一份合法快照作为恢复备份；导出可保留多个生涯。
- 完整状态作为一个 envelope 写入 localStorage，避免金币和库存分别保存。通过单个应用写队列串行处理命令。
- 存档只保留当前比赛完整事件；历史比赛保留输入快照、种子、比分、box score与少量关键事件，必要时按相同版本重演，不累计保存所有逐回合全文。活动快照目标小于1 MiB，原档＋备份合计目标小于2 MiB；超过预算先优化结构，仍需处理实际配额失败。
- 同时打开两个页面时只允许一个可写页：首发要求浏览器支持 Web Locks，以固定锁名持有当前存档写权限。取不到锁的页只读，可显式重试；取得锁后重新读取最新存档。锁API不支持则只读并给出兼容浏览器说明，不自行用心跳猜测互斥。关闭页面后锁由浏览器释放。新开档、导入和所有命令共用该锁与应用写队列。
- 写入失败（空间不足/受限模式）不发布新状态；明确告诉玩家本次操作未保存。
- JSON 导入先做2 MiB上限检查、schema、版本、ID引用、数值边界和经济不变量校验，全部通过才替换；失败保留原档。测试必须测完整三季实际序列化大小和写入成功，不能只靠估算容量。
- 未知高版本不自动兼容；数据版本变化不能静默重算旧档。首发只支持本版本，后续迁移需单独实现。
- 刷新可恢复已保存战斗结果；动画播放进度不需要保存。
- 新开档前提示导出旧档；取消不能删除原档。

## 6. 多 Agent 协作与代码规范

### 6.1 并发编组（最多四个活跃 Agent，含 Lead）

| 阶段 | Lead | 子 Agent 1 | 子 Agent 2 | 子 Agent 3 |
|---|---|---|---|---|
| 契约准备 | 架构、规则、夹具、store接口 | 数据可得性检查 | 视觉方案与组件样张 | 暂不占用 |
| 主并行期 | 接线、存档、集成、解阻塞 | Data | Domain | UI |
| 收敛期 | 发布包、规则复核、合并 | 数据尾项后转 QA | 修复模拟/平衡 | 修复UI后转交付文案 |

子 Agent 不自行再开子 Agent。新角色使用已空闲槽位，不能假定有无限并发。负责人持续整合，不能等三个人都做完才首次联调。

### 6.2 共享工作目录纪律

- 默认同一工作目录按文件归属隔离。所有人先读 AGENTS.md、contracts、rules、design-system。
- 子 Agent 不运行全仓格式化、不改 lockfile、不更新依赖、不改公共类型、不重置/清理 Git、不提交他人修改。
- Lead 统一安装依赖、提交里程碑、处理共享文件；需要新增依赖先报用途和现有替代方案。
- 公共契约有问题时提交变更请求：问题、建议字段、受影响模块、迁移方式；Lead 更新唯一来源并通知全部消费者。
- 测试使用的临时文件放 `work/` 或项目忽略目录，不把临时导出混进产品数据。
- 如果改用 worktree，由 Lead 创建和分配，子 Agent 只提交自身范围；Lead 串行整合。不得一部分 Agent 共享目录、一部分自建副本而没有记录。

### 6.3 代码风格

- TypeScript strict，避免 `any`；外部 JSON 先校验再进入类型层，不靠 `as` 伪装正确。
- Vue 统一 Composition API、`<script setup lang="ts">`；不混 Options API。
- 函数/变量 camelCase，类型/组件 PascalCase，普通模块 kebab-case；组件文件 PascalCase.vue。
- Prettier：2 空格、单引号、分号、统一尾逗号；实际由配置驱动，禁止各自习惯覆盖。
- domain 不导入 Vue、Pinia、DOM、localStorage、fetch；不读系统时间，不使用 Math.random。
- UI 不包含评分公式、奖励规则、抽样逻辑；这些只在 domain/config。
- 金币、属性、奖励都是整数；概率为浮点但必须 clamp，边界不得出现 NaN/Infinity。
- 领域函数返回 Result；预期业务错误不靠异常控制。未知错误统一记录并提供可恢复界面。
- 每个模块只处理一个职责；单文件超过约 350 行先审查拆分，避免机械拆出大量空壳。
- 注释重点说明规则原因/统计假设；不写重复代码行为的逐行注释。
- 禁止 `v-html` 渲染球员名/导入内容；用户自定义名字只按文本显示。
- 每完成一张任务卡就运行相关测试。没有新改动/新失败时不无意义反复跑全套。

### 6.4 交接格式

每个 Agent 完工报告必须包含：任务 ID；修改文件；接口变更（应为无，或附已批准记录）；实际运行的检查和结果；可复现示例；已知问题；下一个接手者需做的事。

“已写测试”不等于“测试通过”；“构建成功”不等于“本地下载版玩通”；不得用这类表述替代真实证据。

## 7. 前端设计规范：同一个游戏，不是多套页面拼起来

### 7.1 视觉方向

采用“篮球球探工作台＋球员卡收藏册”：深色球场背景、暖白信息文字、橙色主要操作、少量球场线条。强调数据、卡片和赛季成长。避免整屏霓虹渐变、不同页面不同阴影/圆角、随机卡面插画。

UI Agent 是视觉唯一负责人。其他 Agent 需要页面时复用共享组件，不自行造按钮、弹窗和卡片。

| 强调色 | `--accent: #FF9B45`; 橙底按钮使用深色文字 |

| 分隔线 | `#394454` |

| 圆角 | 控件 8px、卡片 12px、面板 16px |
| 正文字号 | 14/16px；数据 24/32px；标题 24/32px |

### 7.3 共用组件与状态

必须先交付 `BaseButton`、`BaseDialog`、`StatBar`、`AttributeGrid`、`PlayerCard`、`CoinBadge`、`EmptyState`、`InlineAlert`、`ToastRegion`、`AppShell`。

- 按钮固定 primary/secondary/ghost/danger 四种，统一高度、loading、disabled、focus。

- 属性比较使用“当前 → 预览”，增量有数字和箭头，不能仅靠红绿区分。
- 雷达图由 SVG 绘制，九轴固定排序，旁边保留可读数字列表。

- 无图像资源时仍需完整卡片样式，不能出现破图占位。

### 7.4 页面与必备状态

| 页面 | 核心内容 | 必须覆盖的非理想状态 |
|---|---|---|
| 启动/生涯首页 | 继续、新建、导入导出、数据版本 | 无存档、损坏、旧版本、保存受限 |
| 初始抽卡 | 明星区、普通区、逐张/全部揭晓 | 刷新恢复、不重复抽取、跳过动画 |
| 球员创建 | 九槽、20卡、筛选排序、能力预览 | 缺槽、重复分配、撤销、确认消耗 |
| 生涯主界面 | 自创球员、金币、战绩、下一对手 | 下一场未就绪、生涯结束、只读页 |
| 比赛/结果 | 比分、阶段、事件、个人数据、奖励 | 跳过、模拟失败、重复进入结果页 |
| 卡库/融合 | 来源卡、属性差值、训练成本 | 无提升、卡不足、金币不足、属性满值 |
| 抽卡商店 | 两种卡包、定向位置、概率 | 余额不足、重复点击、已到账恢复 |
| 赛季/生涯总结 | 实际数据、冠军、能力成长、来源 | 未晋级、无某项统计、导出失败 |

布局：桌面主内容最大宽度约 1440px；创建页为卡库＋能力面板双栏。手机改为属性面板与卡库分区，点击完成选择，不能只支持拖拽。测试 1440×900、1024×768、390×844；页面不能横向溢出。

UI 文案统一使用“明星球员”“能力继承”“训练”“金币”“赛季”。避免同一机制出现融合/合成/吞卡等多个名称。面向用户不出现 seed/schema/reducer 等技术术语。

## 8. 可直接分派的任务卡

每张任务的“完成”同时要求文件产出、实际检查、交接记录。Lead 有权拒绝只交页面截图或只交代码文本的结果。

### L0：基础契约与工程骨架（Lead）

- 输入：用户批准的本方案。
- 工作：建立工程、锁版本、AGENTS.md、目录、类型/schema、平衡配置、RNG接口、fixtures、UI service接口、脚本空位；生成docs/rules.md作为本方案第2/3节的实施版本，并核对其与balance.ts一致。
- 产出：契约 v1＋一个以 fixture 展示的可启动页面＋最小检查脚本。
- 验收：各角色能导入同一套类型；示例失败命令不修改状态；依赖安装和构建通过。
- 解锁：D1/G1/U1。未冻结接口不进入三方大规模编码。

### D1：完整球员快照和评分（Data Agent）

- 输入：字段契约、纳入规则、位置分组、评分口径。
- 工作：先确认数据可得性；生成来源清单；完整名单；评分方法；明星池；override；验证脚本。
- 验收：30队逐人对账、无重复 ID、九维齐全且在范围、来源和估算标识齐全、明星及各位置子池可抽取。
- 禁止：修改 domain、制作不同字段名、用模型编造真实球员事实、以 fixtures 冒充完整数据。
- 输出附：实际人数、asOfDate、缺失字段统计、estimated比例与理由、抽查 20 名球员记录。

### G1：抽卡、库存、融合与经济（Domain Agent）

- 输入：契约 v1、balance、fixtures。
- 工作：初始无放回抽样；后续按池抽样；分配校验；继承训练；命令状态校验；奖励纯函数。
- 验收：20卡恰好5星、九张不同实例、库存/金币守恒、失败不变更、相同种子结果一致。
- 禁止：保存 localStorage、改 store、在 domain 中写 UI 文案和异步网络逻辑。

### G2：比赛与赛季（Domain Agent，G1后）

- 输入：统一模拟规则、四种打法、对手模板。
- 工作：实现回合事件、数据聚合、赛程/加时/季后赛、赛后分析；完成参数敏感性检查。
- 验收：比分与事件一致、统计不变量成立、完整生涯跑通、同输入可复现、九项属性均有可检测作用。
- 需上报：无法在合理范围内校准的公式；不得改用总评随机胜负掩盖问题。

### U1：设计系统与创建流程（UI Agent）

- 输入：tokens、共享组件清单、fixtures、service接口。
- 工作：组件样张页；启动、初始抽卡、九维分配；键盘/移动布局。
- 验收：三个视口无溢出；可点击不用拖拽；完成九项并预览消耗；复用组件不重复造样式。
- 禁止：直接操作金币/随机数，硬编码真实20卡，私改全局类型。

### U2：赛季、卡库和结果（UI Agent，U1后）

- 工作：生涯主界面、比赛结果、商店、继承训练、总结、错误状态。
- 验收：以真实 service 玩通首季；刷新和导入错误都有清楚反馈；真实数据名长短不破坏卡片布局。

### L1：应用服务、存档与集成（Lead，与主并行期同步）

- 工作：统一命令入口、事务式状态提交、Pinia接线、存档版本校验、写页锁、导入导出、错误恢复。
- 验收：双击不双扣费、刷新不重发奖励、多页不会同时写、存储失败不假成功。
- 每完成一个垂直流程立即联调，优先“创建→第一场→奖励→抽卡”。

### Q1：独立验收（QA Agent，数据任务结束后接棒）

- 输入：候选构建、规则、验收矩阵；不得只读开发者自述。
- 工作：核心集成回归、损坏存档、离线启动、不同视口、固定种子对比、全量数据抽样。
- 产出：`docs/qa/report.md`，逐项 pass/fail/not-run，截图/日志位置，阻断问题列表。
- 修复策略：QA提交复现与期望；归属 Agent 修复；QA复测。QA不悄悄修改公共逻辑绕过验收。

### R1：本地包与文档（Lead/Delivery Agent）

- 工作：预构建静态资源＋启动器、中文说明、源码复现命令、版本/校验和、教程与创作说明。
- 验收：干净目录解压后无需 npm install 能玩；断网能完成核心流程；教程截图与此版本一致。
- GitHub：准备 README、发布说明、文件清单和目标仓库建议，待发布阶段再执行远程写入。

## 10. 三天推进节奏与闸门

从方案批准后、运行环境和数据来源检查开始计时，不把用户审核等待计入工期。每天按约 8 小时有效工作窗口规划，实际受数据访问和验收结果影响。三天是目标，不是未经验证的完成保证。

| 时间 | Lead | 并行工作 | 当段退出条件 |
|---|---|---|---|
| D1 0–2h | 契约/骨架/夹具 | 数据可得性；视觉样张 | G0：接口完整、数据路线可行、样式统一 |
| D1 2–6h | 命令服务/存档 | D1数据、G1规则、U1创建 | 创建闭环可联调，失败不扣资源 |
| D1 6–8h | 第一条垂直流程 | 最小比赛、页面接线 | G1：20抽→建人→第一场→奖励→存档恢复 |
| D2 0–4h | 处理契约缺口 | 完整数据、赛季/融合、商店结果页 | 数据正式验证通过，首季完整 |
| D2 4–8h | 参数审查和联调 | 三季流程、统计/经济测试、响应式 | G2：全功能可玩，不能再新增P0机制 |
| D3 0–3h | 集成修复 | 独立QA、数据抽查、UI验收 | 阻断级问题清零 |
| D3 3–6h | 离线打包 | 教程/创作说明/真实截图 | G3：干净目录下载包玩通，文档齐 |
| D3 6–8h | 最终审查、交付用户 | 修复回归、准备发布材料 | G4：本地成品待用户验收，未自动发布 |

### 10.1 闸门失败怎么处理

- D1 数据可得性失败：继续用明确标记的 fixtures 做机制和UI；同时解决数据来源。不能把正式范围偷偷缩小。
- D1 第一条流程失败：停做动画/海报，优先打通状态和保存；不堆更多页面。
- D2 末仍有P0缺口：删除P1、视频和运行时AI，不删存档正确性、完整名单和核心闭环。
- D3 包验收失败：继续修包，不发布一个只有开发机能跑的 Release。
- 必需范围无法按时完成时，给用户具体剩余项和可运行原型，明确未满足项，不伪称全部完成。

## 11. 验收矩阵与验证证据

### 11.1 关键规则测试

| ID | 场景 | 合格标准 |
|---|---|---|
| DATA-01 | 全量数据 | 与来源名单逐人对账、无重复/缺九维/非法位置 |
| DRAW-01 | 1000个固定种子开局 | 每次20人物不重复，恰好5星15普通 |
| DRAFT-01 | 同一卡分配两项 | 被拒绝；原分配、金币和库存不变 |
| DRAFT-02 | 确认九项 | 消耗9，库存11，九项值和来源正确 |
| ECON-01 | 钱不够/双击抽卡 | 不透支；同一commandId只出现一个结果 |
| FUSE-01 | 来源更低/同值 | 不允许继承，不消耗 |
| FUSE-02 | 继承与训练 | 只修改目标属性，实例消耗与金币一致 |
| MATCH-01 | 相同输入与种子 | 事件、比分、奖励逐项一致 |
| MATCH-02 | 统计核对 | 队伍得分等于队员得分之和；得分=2×两分命中+3×三分命中 |
| MATCH-03 | 边界与加时 | 命中≤出手、篮板来自未中、盖帽对应未中、平局进入真实加时 |
| CAREER-01 | 晋级/淘汰/两胜系列赛 | 场次、阶段、奖励符合规则，无幽灵比赛 |
| SAVE-01 | 结果页刷新/再次进入 | 金币和奖励不重复，历史数据不变 |
| SAVE-02 | 损坏/未知版本导入 | 保留原档，解释错误，不自动重开 |
| SAVE-03 | 多页和存储失败 | 只允许一页写，保存失败不显示假成功 |
| OFFLINE-01 | 断网启动与游玩 | 无外部必需请求；建人、赛季、抽卡、保存可用 |
| RELEASE-01 | 干净目录解压 | 不用node_modules、不用npm install，按README启动成功 |

### 11.2 平衡验证（不代替玩家试玩）

- 用固定测试种子集跑至少 200 个完整生涯，统计初始九维均值、三季胜率、冠军率、金币收入、抽卡次数和属性分布。
- 测试两种可解释分配策略：按属性顺序贪心、优化总属性匹配；不能只测试随便选卡就推断所有玩家体验。
- 关键关注：开局是否几乎都轻松夺冠、失败者是否有足够金币抽第一包、第二季是否还能获得明显成长、某种打法是否全面碾压。
- 初始建议校准目标：中位开局首季常规赛胜率约35%–70%；输球玩家不晚于第5场获得一次普通包预算；明显强于对手的配置应有统计优势但非100%稳赢。目标可经试玩调整并留记录。
- 单独提高一项属性，在固定环境和多种子下观察对应指标变化；不能要求单场随机结果严格单调。
- 用同种子比较两个版本时，记录规则版本，不能偷偷改公式后覆盖旧结果。

### 11.3 UI与玩家验收

- 三个指定视口截图：创建、比赛结果、融合、赛季总结。
- 键盘可完成选择与确认；焦点可见，数字不只靠颜色。
- 让 3–5 位目标玩家尝试：能否理解一卡一项、是否知道为什么输、是否主动改造再来一季。
- 记录观察，不诱导“觉得好不好玩”；未实际招募到人则标记未验证，不伪造用户反馈。
- 自动化测试与人工截图都有具体版本、时间、环境；公开报告清楚区分 passed、failed、not run。

## 12. 本地运行包与 GitHub 发布计划

### 12.1 首发运行方式

下载版结构：

```text
hoop-forge-v0.1.0/
  dist/                   # 全部预构建资源和球员数据
  start.mjs               # Node内置http静态服务器，无第三方运行依赖
  start.command           # macOS便利启动脚本
  start.bat               # Windows便利启动脚本
  README-开始游玩.md
  VERSION.json
  SHA256SUMS.txt
  THIRD_PARTY_NOTICES.md
```

- 玩家先安装 Node.js 24 LTS，再解压；命令行兜底为 `node start.mjs`。说明明确：这不是免运行环境的原生安装包。
- 便利脚本只负责切换到自身目录并启动；不能自动下载或安装软件。macOS脚本执行位和Windows路径/空格需验证。
- 启动器和便利脚本的源模板统一位于scripts/release，由Lead/Delivery维护；打包程序把它们复制到发布包根目录。不得由UI另写启动入口或在public中放另一套启动器。
- 只监听 `127.0.0.1`，默认固定端口 4178；不绑定局域网地址。端口占用要明确提示，不悄悄换端口导致玩家误以为存档消失。
- 固定使用 `http://127.0.0.1:4178`，不一会儿localhost一会儿IP；两者是不同存储来源。
- 静态服务正确设置 MIME、路径边界，只服务dist，不能通过URL读取任意本地文件。
- 双击 index.html 不是受支持的启动方式；所有图片/字体/脚本/数据随包包含，不依赖CDN。
- 运行不需要账户、网络、模型Key。可选AI报道若未来加入，必须独立开关，失败不能影响赛季。

### 12.2 源码开发方式

计划命令：`npm ci`、`npm run dev`、`npm run typecheck`、`npm run lint`、`npm test`、`npm run validate:data`、`npm run build`、`npm run package:local`。命令要真实写入 package.json 并验证，不能只出现在 README。

依赖精确解析后提交 lockfile，后续使用 npm ci；只由 Lead 升级。初始源码安装需要网络，玩家预构建包运行不需要；文档分开讲。

### 12.3 GitHub目标产物

1. 源码仓库：README、运行说明、玩法、数据方法、许可与来源、截图、验证记录。
2. 版本 tag 与 Release：预构建zip、校验和、更新说明、已验证平台。
3. CI：类型检查、lint、domain/集成测试、数据验证、构建；再打包候选产物。
4. GitHub 自动提供的源码 ZIP 不能代替可直接游玩的预构建包。
5. 测试支持声明必须准确：本机实测macOS；Windows应使用可用环境或后续CI执行启动冒烟检查，没跑不能写“已实测”。启动测试和完整GUI体验也需区分。

### 12.4 发布顺序与用户审核

当前仅提交本方案。方案批准后本地开发；完成后给用户可玩包、源码与验证报告审核。用户确认发布时再确定 GitHub 账号、仓库名、可见性、源码许可证与发布资产并执行上传。

发布准备可提前完成，包括README、候选zip、校验和和发布说明，但不提前公开数据或代码。不得将“最终要发布”理解为本轮立即创建仓库的指令。

## 13. 风险、责任人与处理方式

| 风险 | 责任人 | 触发信号 | 处理 |
|---|---|---|---|
| 全量名单/九维依据不齐 | Data＋Lead | 未能逐队核对或大量字段无依据 | 优先补源和显式估算；不假装完整；必要时报告时间影响 |
| 开局过强、成长无意义 | Domain＋Lead | 首季大量无脑夺冠、融合收益极低 | 先调敌人与经济；需要改变初始继承比例时列为规则变更供用户确认 |
| 比赛像随机开奖 | Domain | 九维变化无统计作用、无法解释输赢 | 做属性敏感性测试，修事件概率与报告，不添加虚构解说遮掩 |
| 代码冲突/接口漂移 | Lead | 字段重复、私有版本、lockfile多方修改 | 冻结接口、单写入者、串行整合 |
| 页面像不同产品 | UI＋Lead | 按钮/卡片/颜色体系不一致 | 共享组件和tokens检查，禁止局部重造 |
| 重复结算或坏档 | Lead＋QA | 刷新多拿币、失败丢库存 | 原子状态提交、命令幂等、导入验证、独立回归 |
| 本地包依赖开发机 | Delivery＋QA | zip缺资源/离线拉CDN/需要npm | 干净目录、断网、无node_modules重测 |
| 功能过多拖延 | Lead | D2后继续增加新系统 | 冻结P0，只做修复和交付；P1排到后续 |

## 14. 方案批准后的第一个行动序列

1. 把用户修改写入 decisions.md，明确本方案默认值哪些保留。
2. 检查本机运行环境、数据可得性，选择并锁定实际依赖版本。
3. 建立本地工程与统一 AGENTS.md，不创建远程仓库。
4. Lead 冻结契约、经济参数与共享夹具；UI输出一张创建页样张。
5. 同时启动 Data、Domain、UI 三个工作 Agent，按任务卡限定文件范围。
